# Продуктовая линейка

Помоги человеку понять, какие предложения связать вокруг основного продукта, для кого они полезны и что проверить первым. Линейка - карта решений покупателя, а не обязательный список из шести новых товаров.

Работай одинаково в Claude Code и Codex: один Markdown-источник, один автономный HTML, без отдельных API, платных сервисов и терминальных действий со стороны ученика. Проговаривай термины простыми словами. Красивая карта не подтверждает спрос.

## 1. Восстанови основу

Из существующих файлов прочитай `SOUL.md`, `USER.md`, `MEMORY.md`, релевантные дневники последних трёх дней в `memory/`, `knowledge/my-product.md` и уже начатый `knowledge/product-line.md`. `knowledge/product-choice.md` нужен для уточнения прежней проверки спроса; `knowledge/my-expertise.md` - только если есть вопрос о выполнимости. Всю базу не загружай.

Собери известное: основной продукт, покупатель и его задача, результат, цена/условия, факты спроса, существующие предложения и ограничения. Сохраняй источники и даты; не обнуляй прежние доказательства. Если память и новый запрос расходятся, уточни, какая версия актуальна.

- Нет выбранного продукта и человек не знает, что продавать: направь к `product-selection`, не изобретай подтверждённую основу. Не устанавливай другой скилл без запроса.
- Есть реальное предложение из рассказа, но нет файла: работай с рассказом, не заставляй проходить курс заново.
- Продукт пока гипотеза: можно сделать черновую линейку; статус спроса от этого не меняется. Первым тестом может быть прямое предложение основного продукта.
- Уже есть линейка: найди точку продолжения, не запускай интервью с нуля.

Выбор и проверка продукта остаются задачей `product-selection`, полная упаковка одного предложения - `product-packaging`. Здесь связывай предложения и используй их текущие условия, не дублируй работу соседних навыков.

## 2. Покажи первый черновик и уточни пробелы

Коротко объясни: «Возьму известное из памяти, соберу вокруг основного продукта понятные предложения и выберу, что проверить первым». Покажи основу в нескольких строках и, если данных достаточно, первую карту. При неизвестном основном продукте или покупателе сначала выясни именно это.

Задавай один вопрос за раз, только когда ответ меняет решение. Предлагай 2–3 подходящих варианта и свободный ответ. Не отправляй весь список ниже как анкету и не переспрашивай сообщённое:

1. Какой основной продукт и для какого покупателя берём?
2. Что уже покупают и на каком шаге люди останавливаются? Если продаж нет - к кому можно обратиться для проверки?
3. Что полезное человек может получить до большой покупки? Он знакомится с проблемой, сравнивает решения или готов пробовать?
4. Какую небольшую законченную задачу можно решить за отдельную плату? Что остаётся основному продукту?
5. Кому нужна более полная помощь? Какая соседняя задача возникает? Почему человек отказывается?
6. Сколько времени, прямых расходов и участия клиента нужно для выполнения?
7. По чему видно, что следующий продукт уже уместен? На ком и что проверим первым?

Плашки используй только при полезной развилке: доступный инструмент вопросов Claude Code или Codex. Если его нет, тот же выбор дай обычным нумерованным сообщением. Не обещай всплывающее окно в неподдерживаемой среде.

Если запрос точечный, доработай нужную связь или входное предложение; не навязывай полную матрицу. Если человек хочет остановиться, покажи найденное и неизвестное, согласуй сохранение черновика и точку продолжения.

## 3. Разложи предложения по ролям

Для полной линейки рассмотри шесть ролей. По каждой объясни решение: используем сейчас / проверяем позже / не нужна. Ненужная роль не должна превращаться в фиктивный товар или пустую карточку. Для точечной задачи рассмотри только относящиеся к ней роли и явно обозначь объём работы.

| Роль | Что проверять |
|---|---|
| Основной продукт | Выбранная задача, покупатель и результат; текущие реальные цена и состав сохраняются |
| Лид-магнит | Бесплатный вход решает небольшую задачу и привлекает будущего покупателя, а не любого любителя бесплатного |
| Трипваер | Первая небольшая покупка даёт законченный результат; её цена оправдана выполнением, символическая стоимость не обязательна |
| Апселл | Более полный вариант: отличается объёмом, участием продавца, результатом или скоростью; может предлагаться при выборе |
| Кросс-селл | Дополнение решает соседнюю задачу; без него основной продукт всё равно выполняет своё обещание |
| Даун-селл | Доступная альтернатива после выяснения причины отказа; при ненужном результате скидка не помогает |

Тариф - вариант того же решения, рассрочка - условие оплаты. Не выдавай их за новые самостоятельные продукты. Подписка и повторная покупка уместны только при реальной повторяющейся задаче.

Перед детальным проектированием прочитай подходящие разделы [references/design-checks.md](references/design-checks.md): роли, вход, маршрут ученика и связи. Не требуй установки сторонних marketing skills: адаптированная методика уже здесь.

## 4. Спроектируй полезный вход

Проверь, нужен ли отдельный лид-магнит/трипваер. Уже готовому покупателю может подойти прямое обсуждение или основной продукт. Новичку не нужно сначала создавать большой бесплатный ресурс и искать поток посетителей.

Если вход нужен, предложи до трёх разных замыслов и объясни выбор одного. Формат подбирай к действию: проверить процесс - чек-лист; подготовить документ - шаблон с примером; понять ситуацию - диагностика; увидеть работу - демонстрация; попробовать - ограниченная проба. Для AI/SaaS допустим инструмент, но сначала оцени создание, поддержку и ручную альтернативу.

Для выбранного входа дай содержательный бриф: получатель/ситуация, проблема, обещанный результат, честное название, формат с обоснованием, структура содержания, пример одного полезного элемента, способ получения, приглашение к следующему шагу и проверка на пользователе. При прямом входе вместо фиктивного бесплатного материала объясни решение и подготовь приглашение к реальному предложению.

Лид-магнит и трипваер должны быть полезны без продолжения. Не обрывай решение намеренно, чтобы вынудить купить. Мысль «за это было бы не жалко заплатить» помогает проверить добротность, но не доказывает готовность платить. Полный PDF, курс, бот и приложение автоматически не создаются: здесь проект линейки и бриф, не производство всех продуктов.

## 5. Проверь переходы и выполнимость

Для каждой связи объясни: **полученный результат → следующая реальная задача → уместное предложение → наблюдаемая готовность → одно действие клиента**. Одного скачивания или покупки недостаточно для вывода о следующей потребности. Показывай возможный прямой переход и пропуск лишних ступеней.

Апселл - ветка улучшенного варианта; кросс-селл - дополнение; даун-селл - ветка отказа, а не обязательная последняя покупка. Убедись, что соседние предложения относятся к одному покупателю, не дублируют результат и не прячут обязательные части основной работы в доплатах.

Проверь известные цену, время, прямые расходы, необходимые ресурсы, участие клиента и предел загрузки. Не меняй реальные условия молча. Для новой цены нужны основания и явная маркировка гипотезы. Не хватает данных - запиши пробел и уточни критичное до реальной продажи, не выдумывай экономику. Выручка и разница отдельных расходов не равны чистой прибыли.

Три маршрута:

- Специалист: опирайся на опыт и доступное время; дешёвая персональная работа не должна поглощать всю загрузку.
- Действующий бизнес: сначала инвентаризируй то, что уже продаётся, реальные повторные покупки и причины отказов. Не выдавай предположение о молчании клиентов за установленную причину.
- AI-направление/SaaS: различай демо, пилот, внедрение, тариф и поддержку. Учитывай данные, доступы, расходы и проверку человеком. Будущие функции не называй работающими; не обещай безошибочность или замену сотрудника.

## 6. Выбери один тест и согласуй карту

Выбери ближайшую проверяемую гипотезу и одно действие. Запиши: кому предложить, что показать/дать попробовать, что сделает ученик, какие признаки применения/интереса/оплаты наблюдаем, период и какое решение принять по результату. Число контактов, сроки и порог успеха зависят от доступной аудитории. Небольшой тест не доказывает весь рынок и не гарантирует продаж.

Новые рыночные утверждения проверяй по прямым источникам с датой и границами вывода, когда поиск действительно нужен. Нет источника - честный пробел. Для сборки карты не обязателен интернет. Не запускай рекламу, рассылки, платежи и сторонние сервисы самостоятельно.

Покажи связную карту, обоснования отложенных ролей, неизвестное и ближайший тест. Получи подтверждение перед сохранением. Если человек уже прямо разрешил сохранить черновик или эти изменения, используй это разрешение, не проси повторно. Изменение продукта, сегмента или существенных коммерческих условий сначала согласуй.

## 7. Сохрани Markdown

Канон - `knowledge/product-line.md`. Перечитай актуальную версию, правь только согласованную часть, сохраняй прежние результаты и чужие разделы. При конфликтующих свежих правках останови запись и уточни версию.

Документ содержит:

1. Основу: продукт, сегмент, задачу, ссылку на `my-product.md` при его наличии, дату, объём задачи и состояние карты.
2. Краткую матрицу включённых предложений: роль, название, покупатель, результат, формат, цена/её статус, следующий шаг и приоритет.
3. Карточки: состав/границы, усилия клиента, сроки и их основание, выполнение/расходы, реальные доказательства, неизвестное.
4. Решения по ролям, которые отложены или не нужны; карту переходов и их условия.
5. Бриф выбранного входа или обоснованный прямой вход; один ближайший тест.
6. Что существует, что согласовано, что подтверждено фактами, что гипотеза, реальные результаты проверок и точку продолжения.

Различай **согласование карты**, **готовность предложения** и **доказательства спроса**. Отзыв, скачивание и согласование не превращаются в оплату. Одна оплата не доказывает устойчивый спрос. При отсутствии данных пиши «данных нет», а не нулевые измеренные показатели.

Не переписывай `knowledge/my-product.md` и `knowledge/product-choice.md` ради новой линейки и не создавай второй полный паспорт основного продукта. Если основа изменилась, сначала покажи последствия.

## 8. Пересобери автономный HTML

Результат - `knowledge/product-line.html`, представление актуального Markdown. Скопируй готовый [assets/product-line-template.html](assets/product-line-template.html), не воссоздавай дизайн и логику вручную.

Прочитай контракт JSON в конце [references/design-checks.md](references/design-checks.md). Собери данные только из актуального Markdown. Все перечисленные поля обязательны; неизвестное - явная строка, не домысел. `effort` описывает участие клиента, а расходы и загрузка исполнителя относятся к `costs`/`timing`: не путай стороны. `entryBrief` допускает null, если вход отдельным предложением не проектировался. Ссылки переходов должны вести на существующие `offers.id`.

Замени только значение null в блоке `<script type="application/json" id="product-line-data">null</script>` на JSON. Используй сериализацию библиотеки, экранируй `<` как `\u003c`, чтобы пользовательский текст не закрыл script. Например, в Python: `json.dumps(data, ensure_ascii=False).replace('<', '\\u003c')`. Не собирай JSON склеиванием непроверенных строк. Сам шаблон остаётся неизменным; его исходная копия поставляется с null.

Перед выдачей проверь коды в обоих массивах `offers[].role` и `roleDecisions[].role`: только `core`, `lead-magnet`, `tripwire`, `upsell`, `cross-sell`, `downsell`. Не заменяй их русскими названиями: перевод уже делает шаблон. Проверь уникальность кодов решений и существование адресов переходов; ошибка этих данных скрывает всю карту, даже если текст Markdown верен.

Если доступен Python 3, используй [scripts/render_product_line.py](scripts/render_product_line.py): `python3 <путь-к-скиллу>/scripts/render_product_line.py - knowledge/product-line.html` и передай JSON через stdin. Вместо `-` можно указать временный JSON-файл. Скрипт без сторонних библиотек проверяет контракт, безопасно вставляет данные в готовый шаблон и сохраняет HTML только после успешной проверки. При ошибке исправь данные по актуальному Markdown и повтори запуск; прежний HTML остаётся целым. Без Python используй описанную выше сериализацию доступной среды и проверь тот же контракт; не заявляй о запуске скрипта, если его не было. Временный JSON не становится второй базой знаний.

HTML работает без сети и сервера: карта/таблица, карточки, разные виды связей, бриф, тест, копирование с ручным запасным способом, печать/PDF. Он может содержать внутренние заметки, поэтому не отправляется клиенту автоматически. Это представление, не отдельная редактируемая база.

Открой HTML, если среда позволяет. Проверь карту/таблицу, раскрытие, копирование, печать, мобильную ширину и соответствие Markdown. Если браузер недоступен, честно обозначь, какие взаимодействия не проверены. Сбой HTML не должен уничтожить Markdown или превратиться в заявление «всё работает».

## 9. Зафиксируй продолжение

При подтверждённом решении точечно обнови существующий `MEMORY.md`: приоритет и ссылка на линейку; допиши итог и точку продолжения в существующий `memory/`. Не создавай эти файлы вне агента только ради навыка. `USER.md` и `SOUL.md` не меняй. Личную память не публикуй в GitHub.

В конце коротко покажи линейку, причины выбора, оставшиеся гипотезы, ссылки на Markdown/HTML и одно ближайшее действие. Промежуточный результат называй черновиком. Доход, рост конверсии, окупаемость, цены, кейсы и спрос не выдумывай.
